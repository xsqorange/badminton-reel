# 踩坑记录

本项目开发过程中所有**失败的尝试**与最终解法。
保留失败记录的目的:换个场地、换批素材时,不用重走一遍。

---

## 一、画质 / 编码类

### 1.1 成片 1.5GB 超大 ⭐⭐⭐

**现象**:5 分 29 秒的成片 **1596 MB**,比源素材(源 5 分钟才 700MB)还离谱。

**排查**:
```bash
ffprobe -select_streams v -show_entries stream=bit_rate ...
# 成片: 39,207,022 bps (39 Mbps)
# 源:   11,950,539 bps (12 Mbps)
```
码率是源的 3.3 倍。

**根因**:`-cq 17 -b:v 0` 配 `-rc vbr`。
NVENC 的 VBR 模式下 `-b:v 0` 的含义是**没有码率上限**,而 `-cq 17` 又要求高质量。
羽毛球是全画面高频运动,每帧都难压,码率直接顶满。
而且这是**两阶段编码**(切片 + 拼接),各放大一次。

**解法**:
```bash
-cq 22 -b:v 0 -maxrate 12000k -bufsize 24000k
```
**`-maxrate`/`-bufsize` 必须同时给**,否则 `-b:v 0` 就是无限制。

**对照实验**(同一段 20s 高运动素材,源 12Mbps):

| 方案 | Mbps | 6分钟估算 |
|---|---|---|
| `-cq 17 -b:v 0`(初版) | 20.8 | 842 MB |
| `-cq 23 -b:v 0` | 9.8 | 398 MB |
| `-cq 22 -maxrate 12M` | 11.0 | 445 MB |
| `-cq 24 -maxrate 12M` | 8.4 | 341 MB |
| `-cq 26 -maxrate 10M` | 6.4 | 260 MB |

**画质验证**:100% 像素裁切对比(球衣衣褶、球拍线、空调纹理),
cq17 / cq23 / cq24 / cq26 **肉眼完全分不出**。多出来的 3 倍码率是纯浪费。

### 1.2 画面卡顿("一卡一卡") ⭐⭐⭐

**现象**:成片观感明显卡顿。

**第一直觉**:时间戳断裂。**实测排除**:
```
qc_smooth.py → median_gap=16.667ms  std=0.000ms  顿挫帧 0
```
时间戳完美。

**真凶**:帧间内容。`exp_stutter.py` 测出旧版成片有 **12485 个静止帧**
(diff < 0.01,即画面完全不动)。

**根因**:`-r 60 -vsync cfr` 把 VFR 源强转 CFR 时,
ffmpeg 丢弃运动帧后**用复制帧补齐**,画面就定住了。

**解法**:
```bash
-vf "fps=60:round=near:start_time=0"     # 基于时间戳等距重采样
```

**对照**:
| | 静止帧 | 变异系数 |
|---|---|---|
| 旧方案 | 12485 | 2.264 |
| 新方案 | 6 | 0.559 |

> **教训**:判断卡顿要测**帧间内容相似度**,不是时间戳。

---

### 1.3 `concat demuxer + -c copy` 导致时间轴断裂

**现象**:拼接后画面顿挫。

**原因**:concat demuxer 按各文件的**容器时长**算偏移,而 VFR 源的时长有取整误差,
累积起来就断了。

**解法**:用 **concat filter**(所有片段在同一条 filter_complex 内,共享一条时间轴):
```bash
[0:v][1:v]...[N:v]concat=n=N:v=1:a=0[cat];[cat]fps=fps=60:round=near:start_time=0[outv]
```

---

### 1.4 单个 filter_complex 放 31 个 trim 太慢

**现象**:15 分钟还没跑完。

**原因**:trim 分布在整个 3688s 时间轴上,ffmpeg 仍要**从头顺序解码**,无法跳过。

**解法**:两阶段 —— 先逐段 `-ss`(输入端秒级跳转)切出规范化片段,再 concat filter 拼接。

---

### 1.5 SSIM/PSNR 滤镜返回 99 或 0

**现象**:`psnr` 输出 `average:99.00`,`ssim` 输出 `All:0.00000`。

**原因**:参考文件与被测文件的**帧率/时基不一致**(参考用 FFV1 无 `-r 60`,被测强制 CFR 60),
滤镜对不上帧。

**解法**:统一所有输出的 `-fps_mode cfr -r 60`,或干脆放弃数值指标,
用 **100% 像素裁切并排图**目视对比(更可靠,尤其对编码参数选择)。

## 二、算法 / 选段类

### 2.1 用运动能量选高光 → 质量差 ⭐⭐

**现象**:选出的多是 1-2 拍短促对抗,还混进换人、走动。

**根因**:运动能量高 ≠ 在打球。

**解法**:改用**击球瞬态检测**,以「回合」为单位选段(见 README 第二节)。

---

### 2.2 用运动能量找回合边界 → 159 个回合被判起点不明 ⭐⭐

**现象**:`start_unclear` 159 / `end_unclear` 51,几乎全军覆没。

**根因**:羽毛球是**连续对打**,回合间隙(捡球/换发球)极短,
画面运动能量**几乎不会降到"静止"**。

**解法**:放弃运动能量判据,改用音频的**局部相对能量**(见 2.3)。

---

### 2.3 用绝对静默期找边界 → 永远找不到 ⭐

**现象**:`gap_after` 恒为 0。

**根因**:诊断发现这段录像**全程有持续的场地背景噪声**:
```
RMS 分布 p10=-6.7  p25=-6.7  p50=-6.7  p75=-6.7  p90=-6.7
```
(注:这是绝对 dB 之外的另一个统计,核心结论是**背景噪声恒定存在,不存在绝对静默**)

**解法**:用**局部相对能量**:
```
相对能量 = 音频RMS - 5s滑动均值(消除慢漂移) → 归一化
起点 = 从第一拍往回,直到相对能量回升到基线以上(发球准备)
终点 = 从最后一拍往后,直到相对能量跌回基线以下(得分后收尾)
```

---

### 2.4 自动遮挡检测 5 种方案全失败 ⭐

试过的方案:

| 方案 | 失败原因 |
|---|---|
| 帧差比(中心区 vs 全图高频比) | HEVC 压缩噪声淹没高频信号,实测所有候选比值几乎相同(0.93~0.95) |
| 肤色 blob(v1,宽阈值) | 紫色地板/墙面全部落进 YCrCb 肤色区间,整块画面被判为肤色(blob≈0.30) |
| 肤色 blob(v2,收紧阈值+限定下半部) | 暖光下地板仍命中,无区分度 |
| 高频能量集中度 | 同方案 1,压缩噪声主导 |
| 人脸检测(Haar) | OpenCV 5.0 移除了 `CascadeClassifier`;换 `FaceDetectorYN` 需额外模型文件,且远景人脸检不出 |

**最终方案**:自动规则初筛 + **联系表人工核验**。
每回合抽首/中/末三帧拼成一行,一眼看出是否切在中间、是否有人挡镜头。

> **教训**:暖色调照明的体育场馆,肤色分割不可靠。别和物理规律对抗。

---

### 2.5 发球太轻被瞬态检测漏掉

**现象**:片段起点在第一击处,没拍到发球动作。

**原因**:羽毛球发球是软击,能量低,自适应阈值把它过滤掉了。

**解法**:固定回溯 `MIN_LEAD = 0.9s` 覆盖抛球+发球动作,
同时用 `MAX_LEAD = 1.4s` 防止过度回溯(前面若不是静止就说明边界不可信)。

## 三、工程 / 流程类

### 3.1 3号场开头混入 2号场视频 ⭐⭐

**现象**:3号场成片开头 17.8 秒是 2号场的画面。

**定位方法**:把成片第一帧与两场源文件第一帧分别抽帧对比,**完全一致**。

**根因**:两个构建任务**并发共用同一个临时目录** `_build`。
2号场在失败(文件锁)前已写入 `seg000/seg001`,3号场拼接时读到了它们。
2号场前两段正好 7.6 + 10.2 = **17.8 秒**,与现象完全吻合。

**解法**:
1. 每个成片用**独立临时目录**(`_build_<成片名>`)
2. 构建任务**串行**执行,不要并发

---

### 3.2 PowerShell 里写 bash 语法

**现象**:`cd X && for f in *.mp4; do ...; done` 报「循环中缺少语句体 do」。

**解法**:PowerShell 用 `ForEach-Object` + 分号:
```powershell
Get-ChildItem *.mp4 | ForEach-Object { & ffprobe ... $_.FullName }
```

---

### 3.3 ffmpeg 滤镜里的冒号

**现象**:`No option name near '110:80:60'`。

**原因**:filter 参数用 `:` 分隔,`crop=160:110:80:60` 里的冒号需要转义,
`metadata=print:...:file=路径` 里的路径冒号也要转义。

**解法**:用 `-filter_complex` 传完整滤镜图 + 转义 `\:`,
或干脆把 `file=` 输出改走 stderr(`metadata=print` 不带 `file=` 时输出到日志)。

---

### 3.4 逐帧 `select='eq(n,...)'` 极慢

**现象**:抽 45 帧跑了 10 分钟没完。

**原因**:`eq(n,...)` 需要从头解码到目标帧。

**解法**:`-ss` 输入端定位 + `-frames:v 1`,一帧一次调用。

---

### 3.5 Python 逐像素处理候选太慢

**现象**:115 个候选 × 57k 像素的纯 Python 循环,15 分钟没完。

**解法**:改用 **ffmpeg 滤镜批量计算**(`tblend=difference` + `signalstats`),
一次调用处理整段。

---

### 3.6 含中文路径时 `Get-ChildItem` 返回空

**现象**:目录明明有文件,`Get-ChildItem` 却列不出来。

**解法**:改用 Python 的 `os.listdir` / `glob`,或 `Get-ChildItem -LiteralPath`。

---

### 3.7 ffmpeg 输出 jpg 报 mjpeg 编码错误

**现象**:`Error while opening encoder - maybe incorrect parameters`。

**解法**:改用 PNG(`-pix_fmt rgb24` + `.png`),或加 `-strict -2`。

---

### 3.8 微信 iLink 通道:桌面端回复发不到微信 ⭐⭐

**现象**:回复里挂了 `<deliver-assets>` 标签,微信侧完全没收到。

**根因**:**桌面端会话的回复走本地渲染,不经过 iLink 出站投递**。
只有微信侧发起的会话,回复才会经 `parseMediaTags → CDN 上传 → sendmessage` 投递。

代码注释原话:
> iLink REQUIRES the inbound message's `context_token` to be echoed back on every outbound.
> Without this, the adapter sends contextToken='' and iLink **silently drops the reply** —
> the symptom is "agent receives, user gets nothing back".

**解法**:直连 iLink API(见 `docs/微信通道.md`)。

---

### 3.9 iLink sendmessage 报 `invalid arguments`

**原因**:把 text 和 video 放进**同一个** `item_list`。

**解法**:**每个 item 单独调一次 sendmessage**(SDK 源码就是这么做的)。

---

### 3.10 iLink 发送成功判据不是 `ret == 0`

**现象**:明明返回了 message_id,脚本却判定失败。

**原因**:成功响应形如 `{"message_id":7522204267208779144}` —— **没有 `ret` 字段**。
`d.get("ret") == 0` 判为 False。

**解法**:判据改为「有 message_id 且 ret/errcode 都不是错误码」。

---

### 3.11 iLink CDN 回查 400

**现象**:`GET /download?encrypted_query_param=...` 一直 400。

**原因**:下载端点需要微信 App 专有凭据,**机器人侧本就无法回查自己上传的文件**。

**解法**:**不能用回查判断发送是否成功**,只看 sendmessage 是否返回 message_id。

---

### 3.12 context_token 取不到

**现象**:context_token 只存在运行时内存,不落盘;`getupdates` 用空游标返回空消息。

**原因**:桌面端 monitor 持续轮询并推进游标,历史消息已被消费。

**意外收获**:实测发现 **服务端不校验 context_token 的值,只要求非空**。
传任意非空字符串(如 `mcode-<timestamp>`)即可。

---

## 四、经验总结

1. **判断卡顿要测帧间内容,不是时间戳。** 静止帧数是最诚实的指标。
2. **VFR 源永远用 `fps` 滤镜,不要用 `-vsync cfr`。**
3. **`-b:v 0` 在 VBR 模式下 = 无上限**,必须配 `-maxrate`。
4. **物理事件检测 > 视觉运动检测。** 击球声比画面运动更能说明"在打球"。
5. **自动检测不可靠时,果断转人工核验。** 联系表让人工成本极低。
6. **并发写同一目录必出竞态。** 独立目录 + 串行执行。
7. **对比实验用像素裁切图,别信失效的 SSIM/PSNR。**
8. **留档失败方案。** 换素材时最省时间的就是这份记录。
