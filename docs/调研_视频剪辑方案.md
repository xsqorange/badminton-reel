## 一、推荐执行路径

> 这一节回答"按什么顺序做"。顺序不可换：后一步的验收依赖前一步的产物。

```
第 0 步 · 固化口径（不动代码）
  Chief 裁定的 §三 口径 A–G 全部转成 eval/ground_truth/*.json 的字段
  → 验收：每个 GT 条目带 annotation_method / annotator / shots_source
                                    ↓
第 1 步 · P0-1 聚类间隙重标定（profile 层，零代码改动）
  analysis.rally_max_gap 1.6 → 2.0
  → 验收：split_rate ≤0.20 且 merge_rate ≤0.15（157 回合口径）
                                    ↓
第 2 步 · P0-2 主球场 ROI 门控（新增 profile 键 + probe_highlights 加 crop）
  四角 homography → motion_roi → 拍数只认与 ROI 运动共现的瞬态
  → 验收：拍数虚高比从 ±(−17%~+39%) 收敛；负样本误判率下降
                                    ↓
第 3 步 · P0-3 人工逐拍真值（新增 eval/ground_truth/c3_shots.json）
  ShuttleSet 式逐拍字段，拍数第一次脱离检测器
  → 验收：≥30 回合 / ≥500 拍，双标注 κ ≥0.7
                                    ↓
第 4 步 · P1-1 长回合时长配额 + P1-2 指标补齐
  → 验收：成片 ≤360s 且长回合在片率不降；split/merge/IoU 双档进报告
                                    ↓
第 5 步 · P2 球轨迹交叉验证（TrackNetV3，可选）
  音频漏检由轨迹补，轨迹断线由音频补
```

**为什么是这个顺序**：第 1 步零代码改动、当天可验，先把"长回合消失"这个根因变量隔离出来；第 2 步是拍数可信的前提；第 3 步是前两步的**验收基准**（没有人工逐拍真值，第 2 步的偏差无法量化）；第 4、5 步在有真值之后才有意义。**跳过第 3 步做第 2 步 = 自证**（详见 §四 P0-3）。

## 二、方案对比（候选 / 取舍 / 不适用前提）

> 每条给"换来什么、付出什么"和"什么条件下根本不适用"。末列为与现役树的关系。

### S1 音频击球瞬态 + 能量阈值 ⭐ 现役

- **核心信号**：10ms 短时 RMS 包络 → 一阶差分上升沿 → 局部中位数+offset 阈值 → min_gap 合并 → gap 聚类成回合。
- **取舍**：换来"击球声比画面运动更能说明在打球"（`docs/踩坑记录.md` §四.4），且**拍数直接反映激烈程度**、边界可由局部相对能量定位；付出是**对噪声与阈值极敏感**，且**当前实现未限定主球场**（`src/probe_highlights.py:39-52` 的运动能量无 crop，拍数取自全轨混合音频）⇒ 背景场会同时污染两个口径。
- **不适用前提**：素材为**持续场地噪声**（RMS 恒在 −31dB，无绝对静默）时，绝对阈值法不可用，必须走相对判据 —— 这正是 v5 取代 v4 的原因（踩坑 §2.3）。
- **现役关系**：**已采纳**（`src/detect_hits.py`）。阈值真标定**尚未验证**。

### S2 音频瞬态 + 学习式峰值分类

- **核心信号**：mel 谱图 / MFCC 上的峰值检测 CNN；用**零相位滤波**保证时间精度。
- **取舍**：换来对场地噪声的鲁棒性（不再靠调 dB）；付出是需自建训练集与推理管线，且黑盒后阈值失去可解释性 —— 与本项目"参数可复核、可回归"的取向冲突。
- **不适用前提**：必须有**带标注的击球音频语料**。本项目目前**没有**逐拍音频标注（见 §六 P0-3）⇒ 现阶段不可落地。
- **现役关系**：**尚未验证**（公开实现为乒乓球场景，arXiv 2409.11760 / `cogsys-tuebingen/tt_sounds`）。

### S3 音频 + 惯性（IMU）融合击球检测

- **核心信号**：音频似然序列 + IMU，用时间偏移同步两路。
- **取舍**：换来击球时刻的高精度与高召回；付出是需要**佩戴式硬件**与逐场采集。
- **不适用前提**：**必须有 IMU**。俱乐部录像是**固定机位远景监控**，玩家不佩戴任何设备 ⇒ **本项目根本不适用**。
- **现役关系**：**已否决**（硬件前提不成立，arXiv 1805.05456）。

### S4 球体轨迹追踪（TrackNetV3）

- **核心信号**：逐帧羽毛球像素位置 → 轨迹 rectification。
- **取舍**：换来**从根上解决漏检**（轨迹可推断被漏的拍，进而防止回合被切碎）；付出是需 GPU + 预训练权重，且羽毛球在 1920×1080 远景下像素极少，**其公开指标来自其自有数据集，在我们的固定机位素材上必须先验证**。
- **不适用前提**：目标在画面中的像素尺寸不够（远景/低码率）时不可用；`docs/踩坑记录.md` §2.4 已证明**HEVC 压缩噪声会淹没高频信号**（帧差比 0.93~0.95 无区分度），这对基于高频的球体检测是明确的负面信号。
- **现役关系**：**尚未验证**（`qaz812345/TrackNetV3`，论文自述 P 97.51% / R 96.83% / F1 97.16% / 30 FPS，**未本地复现**）。

### S5 球员轨迹 + 姿态（YOLO11-Pose + ByteTrack）

- **核心信号**：逐帧球员框/骨架 → 场地米制坐标（homography）→ 击球判定。
- **取舍**：换来"这一拍是谁打的、打的是什么球种"；付出是重资产（GPU + 标注 + 权重），且**它解决的是"谁/什么"，不是"第几秒"** —— 我们的目标恰恰是后者。
- **不适用前提**：需逐帧人员标注才能训出可靠模型；固定机位远景下人像很小。
- **现役关系**：**尚未验证**（COURTSIDE `jayclim/BadmintonAI`，MIT，自述球场坐标误差 ±0.57m、双打"四人全在回合内"覆盖率 ≈93%，**项目自述**）。

### S6 比分板 / 得分事件 OCR

- **核心信号**：记分牌文本 → 得分时刻 → 回合边界。
- **取舍**：换来**规则锚点式**的客观边界（进球就是球过线那一刻），比视觉边界稳定；付出是需 OCR 模型 + 版式适配。
- **不适用前提**：**必须有记分牌**。俱乐部日常录像**没有记分牌** ⇒ **本项目不适用**。
- **现役关系**：**已否决**（前提不成立；COURTSIDE 用了它，我们的场景没有）。

### S7 场地单应变换 homography

- **核心信号**：场地四角像素坐标 → 3×3 单应矩阵 → 场地米制坐标。
- **取舍**：换来"画面坐标 ↔ 球场坐标"的公共坐标系 —— ROI 限定、球员轨迹、落点估计**三件事共用它**；付出是每场机位不同 ⇒ 每场要标一次四角（但**固定机位下这是一次性成本**）。
- **不适用前提**：镜头移动或变焦 ⇒ 四角失效，需要有效性自检。
- **现役关系**：**尚未验证**（ShuttleSet `homography.csv` 已存四角点与矩阵，可直接照抄字段设计）。

### S8 运动能量 / 帧差

- **核心信号**：相邻帧差分能量（`tblend=difference` + `signalstats.YAVG`）。
- **取舍**：实现最省；但运动能量高**不等于在打球**（可能是有人走过镜头前、换人、捡球）。
- **不适用前提**：**羽毛球是连续对打，回合间隙极短，运动能量几乎不降到"静止"** ⇒ 边界判据根本不成立（实测 159 个回合起点不明、51 个终点不明）。
- **现役关系**：**已否决**（踩坑 §2.1 / §2.2，v3→v5 的转折点）。⚠ 但**它仍作为选段打分的一个权重项**存在（`src/select_v5.py:240` 的 `max_motion`、`:257-260` 的 `weight_motion`）—— 这与"否决它做边界判据"不矛盾，**边界不用它、打分可以用它**，但它同样是**全画面无 crop** 的值 ⇒ 同样受背景场污染。

### S9 LLM 片段显著性打分（SVHighlights / TF-SELECTOR）

- **核心信号**：把长视频切成语义一致片段 → LLM 读视觉描述 + 字幕 + 音频音量打分。
- **取舍**：换来"不需要逐片段人工标注"的标签生成方式；付出是 LLM 推理成本 + 强依赖字幕/转播镜头切换。
- **不适用前提**：**必须有字幕或官方高光片**。俱乐部录像**两者都没有** ⇒ 信号不存在。论文自述相对 VTG 基线 +2.50 HIT@1 / +4.04 HIT@K / +2.95 IoU，**绝对增益仍是个位数**。
- **现役关系**：**已否决**（前提不成立，arXiv 2606.06926，KDD'26 D&B）。

### S10 视频摘要网络（TVSum / SumMe；Less is More）

- **核心信号**：学习片段重要性，用**视频时长作隐式监督**（越短的视频里的片段越可能是高光）。
- **取舍**：换来"不标注也能训高光检测器"；付出是训练域是 UGC 短视频，迁移到体育录像无保证。
- **不适用前提**：需要大规模带标签语料；本项目是**单场几十到几百个回合**的小样本场景。
- **现役关系**：**已否决**（不可落地），但**指标口径可借**：HIT@1 / HIT@K / IoU、以及"按摘要长度比例 sweep"的评测范式（见 §六）。

### S11 多目标跟踪库（roboflow/trackers）

- **核心信号**：检测 + 跟踪，附带 HOTA / IDF1 指标。
- **取舍**：换来"跟踪质量可量化"（用来验收 ROI/轨迹方案），工程成熟、Apache-2.0；付出是多一个依赖。
- **不适用前提**：不适用场景没有，只适用"要不要引入一个评价尺子"。
- **现役关系**：**尚未验证**（ByteTrack 已被 COURTSIDE 用于同类场景并证明可行）。

## 四、改进建议（按 P0 / P1 / P2）

> 纪律：不动 `config/base.yaml` 既有数值（只允许**新增**键，默认值保持原语义，保住 10/31、11/01 归档基线）；不动 `long_rally_shots = 30`；不新增依赖；不跑 pipeline（会覆盖成片）。

### P0-1 · `analysis.rally_max_gap` 1.6 → 2.0（profile 层，零代码改动）

- **改什么**：`config/profiles/club-2026-11-07.yaml` 新增 `analysis.rally_max_gap: 2.0`（base 保持 1.6）。`src/detect_hits.py` 已通过 `a["rally_max_gap"]` 读参，**不需要改任何 Python**。
- **为什么**（本机实测，157 个人工核验过的真实回合）：当前 G=1.6 把真实回合切成 ≥2 段的比例是 **26.8%（rise4/off6）/ 49.7%（base）**。真实击球节奏 p50≈0.54–0.86s ⇒ 漏一拍就在回合内部留 ~1.1–1.7s 的洞，正好压在 1.6 上 ⇒ **单次漏检即断链**，长回合掉出"≥30 拍"口径。
- **代价曲线**（拆=真实回合被切碎占比，合=一个簇覆盖 ≥2 个真实回合占比）：

  | G(s) | base 拆/合 | rise5off6 拆/合 | **rise4off6 拆/合** | countG 拆/合 |
  |---|---|---|---|---|
  | 1.6（当前） | 0.497 / 0.016 | 0.331 / 0.053 | **0.268 / 0.078** | 0.395 / 0.030 |
  | 2.0 | 0.357 / 0.034 | 0.210 / 0.095 | **0.159 / 0.127** | 0.217 / 0.064 |
  | 2.5 | 0.217 / 0.071 | 0.096 / 0.157 | 0.070 / 0.243 | 0.115 / 0.120 |
  | 3.0 | 0.089 / 0.112 | 0.051 / 0.257 | 0.025 / 0.348 | 0.038 / 0.214 |

  代价最小点（拆+合）：base→**G=3.0**、rise5off6→G=2.5、**rise4off6→G=2.0**、countG→G=2.5。现役 profile 的聚类口径是 rise4/off6 ⇒ **G=2.0**。
- **预期收益**：真实回合腰斩比例 **27.4% → 16.6%**（执行员在逐拍人工真值口径下复跑值；我原报的 26.8%→15.9% 因 GT 在两次运行间变更而略偏，**以 0.274/0.166 为准**）；长回合不再因"内部漏一拍"被切成两段。
- **风险**：合并率 7.8% → 12.7%，**相邻两个回合可能被并成一个"60 拍长回合"，直接放大拍数虚高** ⇒ 必须与 P0-2 同批做，单独上会更糟。
- **验收**：重跑附录 A 命令，`rise4/off6` 的 `split_rate ≤0.20` 且 `merge_rate ≤0.15`。

### P0-2 · 主球场 ROI 门控（画面-音频共现）

- **改什么**（三处，全部在 profile 层 + 一处一行代码）：
  1. 用**场地四角点 → homography**（S7 / ShuttleSet `homography.csv` 字段）标一次主球场 ROI，存 `analysis.motion_roi`；
  2. `src/probe_highlights.py:42` 的 vf 加 `crop=`（**新增 profile 键，base 默认关闭 ⇒ 归档基线不受影响**）；
  3. `src/detect_hits.py` 的拍数只认**与 ROI 内运动活跃共现**的音频瞬态（Chief A4 的 B1 方案）。
- **为什么**：直接消除 Chief F5 的口径错误 —— 运动能量取自全画面、拍数取自全轨混合音频 ⇒ "≥30 拍"量的是"主球场 + 4~5 片背景场"的混合瞬态密度。**这是拍数口径可信的前提**，也是 P0-1 的配套。
- **风险**：ROI 固定，镜头位移即失效 ⇒ **必须加"ROI 有效性自检"**（位移超阈值就报警，不要静默算错）；俱乐部多场同框 ⇒ ROI 必须是 profile 键、每场不同。
- **验收**：拍数虚高比从 ±(−17%~+39%) 收敛；负样本误判率下降；**注意**：在 P0-3 完成前，拍数偏差只能用"ROI 内外命中数比"做间接验收。

### P0-3 · 人工逐拍真值（把"拍数"从自证里拉出来）

### 5.1b ★ 本批实测结论：「≥30 拍」在本批**没有真值样本**

人工逐拍复核后的 `c3_long_rallies.json` 22 条有效条目，**shots 分布 3–18 拍，`shots ≥ 30` 的为 0 条**（人工逐拍最大 **18 拍**）。

⇒ **R4a（≥30 拍召回）在本批是 N/A（n=0），不是"没检出来"，而是"人工真值里这个对象不存在"。**

这与 `docs/踩坑记录.md` §3.16 的旧结论**方向相反、机制相同**：

- 旧结论（§3.16）：检测器把回合**切碎** ⇒ "看起来没有长回合"，实际**有**；
- 本结论：拍数此前被**虚高**（门控前最坏 **2.89×**，最终配置 **1.10×**）⇒ 检测器数出来的 "≥30 拍" 大多**不是真 30 拍**。

⇒ **`select.long_rally_shots = 30` 保持不动是对的**（Chief 裁定 §一.4），但**本批无法用它验收** —— 报告必须写 **n=0 / N/A**，**不得**用"召回率 100%"表述（踩坑 §3.13）。
⇒ 真实长回合的验收只能**跨批累积**（`docs/标注规范.md` §8.2 规则），或另立一个**明确声明的观察指标**（如"本批可达的最长区间"），并在报告里写明**这不是 ≥30 拍口径**。

### 5.2 业界对照：

逐一核查：SoccerNet / SoccerNet-v2（tight mAP δ=1~5s / loose δ=5~60s + shown/unshown 拆分）、SVHighlights（HIT@1 / HIT@K / IoU，训练无关的 TF-SELECTOR）、TVSum / SumMe（帧级重要性分，多标注者取平均）、`Less is More`（arXiv 1903.00859，CVPR'19，用**视频时长作隐式监督**）—— **没有任何一项为"长回合优先"设计过权重或配额**。
⇒ 本项目的"≥N 拍强制入选 + 不受时长预算"是**自创路径**，没有先例可抄。**它要么自证充分，要么自己补齐配额与上限。**

### 5.3 可借的时长约束范式（三个）

| 范式 | 出处 | 做法 | 迁移到本项目 |
|---|---|---|---|
| 容差双档 | SoccerNet 官方套件 | 同指标报 tight / loose 两档 | 回合匹配也报双档（重叠 ≥0.5 / ≥0.3），避免边界差 0.5s 就判全错 |
| 按目标时长条件化 | `Less is More` | 把"我要多长的摘要"作为显式输入 | 选段层引入 `target_duration` 条件，让"凑满 ≤360s"成为打分输入而非事后截断 |
| 片段级显著性 + HIT@k / IoU | SVHighlights | 先切语义一致片段再打分，指标报 HIT@1 / HIT@K / IoU | 本项目的"回合"即等价 segment ⇒ **直接可报 HIT@k / IoU** |

### 5.4 建议的取舍（自定，须写进文档并可复核）

```
现状：≥30 拍 → 无限额强制入选 → 可能撑破 target_seconds
建议：≥30 拍 → 配额内强制 → 超出配额按拍数降序保留 → 落选条目在报告显式列出

长回合时长配额 = min( 长回合总时长 , 目标成片时长 × 长回合配额系数 )
长回合配额系数：初值 0.40（未验证，需在成片上目视定档）
```

**报告必须写明**：长回合门槛（30 拍档）、进入成片的长回合条数与时长、在片时长占成片比例、因配额落选的长回合条目。**不允许只报"召回率 100%"而不报 n**（踩坑 §3.13）。

## 七、明确不建议的方向（为什么不做）

| # | 方向 | 不建议的理由 |
|---|---|---|
| N1 | **引入"长回合优先"权重/配额范式** | **业界没有公开先例**（§五.2 逐一核查过 SoccerNet/SoccerNet-v2、SVHighlights、TVSum/SumMe、Less is More）⇒ 没有可抄的公式，只能自定。**不是不做，是必须自己定义并写清**（§五.4）—— 任何"引用某某论文的权重设计"的说法都应被质疑。 |
| N2 | **用 LLM / segment-saliency 做选段**（S9） | 依赖字幕、官方高光片、转播镜头切换 —— 俱乐部录像**一个都没有**。论文自述相对基线也只 +2.50 HIT@1，绝对值仍是低分。信号不存在，成本却高。 |
| N3 | **端到端深度模型替代音频瞬态做数拍**（VideoMAE / SlowFast 等） | 我们的目标不是"这是不是羽球"，而是"这一拍在第几秒"。固定机位 + 单场百来个回合，标注成本远超收益。COURTSIDE 用 YOLO+ByteTrack 是为了"谁打的、什么球种"，不是为了数拍。 |
| N4 | **IMU 融合击球检测**（S3） | 需要佩戴式硬件，俱乐部固定机位远景不具备 ⇒ 前提不成立。 |
| N5 | **比分板 OCR 做回合边界**（S6） | 俱乐部录像无记分牌 ⇒ 前提不成立。 |
| N6 | **回到运动能量找边界**（S8） | 踩坑 §2.2 已实测证伪：159 回合起点不明、51 终点不明；羽毛球连续对打 ⇒ 运动能量几乎不降。**它可以当打分项，不能当边界判据。** |
| N7 | **继续放宽 rise 阈值（6→4→3）来"救"长回合** | 本轮实测 rise4/off6 的拍数虚高 **+39%**，它把两三个回合连成 60+ 拍 ⇒ "≥30 拍"口径失真（profile 注释已记此教训）。放宽 rise 只是把**漏检**换成**误检**，两个错误互相抵消后长回合还是假的。**正解是 P0-1（gap 重标定）+ P0-2（ROI 门控），不是继续调 dB。** |
| N8 | **自动遮挡检测** | 踩坑 §2.4 已试 5 种（帧差比 / 肤色 blob ×2 / 高频能量集中度 / 人脸检测）**全部失败**；业界亦无可靠方案。保留"自动规则初筛 + 联系表人工核验"（README §二.5）。**别和物理规律对抗。** |
| N9 | **用现有 GT 的 `shots` 标定计数阈值** | `c3_1200-2400.json` 的 `notes` 自陈该字段是"检测器合并估计"。本轮实测显示该量随参考系漂移（base 0.829 / rise4off6 1.394）⇒ **自证**。★**更正**：该 1.394 是拿**检测器派生的**基线比的，系统性偏高；执行员用**逐帧人工真值**复算同一组参数得 **1.10×**，并与我的旧独立计数口径（1.152×）交叉一致 ⇒ **真实虚高约 10%，不是 39%**。结论方向不变（仍不能用检测器派生的 GT 标定），但**幅度按 1.10× 读** |
| N10 | **对 `select.long_rally_shots` 做任何下调** | Chief 裁定 §一.4 明令保持 30；踩坑 §3.16 已记录"本批没有 ≥30 拍回合"是检测器切碎造成的假象。 |
| N11 | **去 MultiSports 找羽毛球标注** | 已核：只有**篮球/排球/足球/艺术体操**，**不含羽毛球**。 |
| N12 | **把 ShuttleSet / BFMD 当我们的 GT** | 场景完全不同（职业转播单打、有记分牌/Hawk-Eye vs 俱乐部多场同框固定机位）；BFMD 标注包**仅限非商用学术研究且禁止再分发**。**只借字段格式与阈值经验，数值不可迁移。** |
| N13 | **拿现成"体育高光生成器"仓库直接用** | 搜索里大量 `Soccer-Highlight-Generator` / `automatic-highlight-reel-generator` 一类：多为课程作业/黑客松 demo，输入是**转播足球**、依赖解说/字幕/换镜信号，多数无标注无评测，README 里的 accuracy 多为自报不可复核。**不要引入。** |
| N14 | **用 REA 逆向商业剪辑软件/移动端 App 的高光检测实现** | 本轮**未执行**（无合适样本、收益低）。理由：逆向得到的是"产品行为"而非"算法"，无法复核、无法迁移；而我们需要的三件事（逐拍标注字段、回合时间线、评测指标）公开实现已全覆盖。**若将来要做，优先级应低于 P0-1/P0-2。** |
| N15 | **新增第三方依赖（如跟踪库、YOLO 权重）到主链路** | §七 P2 只建议在**验证片段**上试，不进主链路。Chief 裁定 §七明令"不新增依赖"。P2 若要推进，须另开一轮并先证明收益。 |
