# 微信 iLink 通道发送视频 · 操作说明

> 用途:通过 MiniMax 内置的微信机器人通道(iLink)向微信会话发送视频/图片/文件。
> 项目内位置:`src/ilink_client.py`(协议核心)、`tools/wx_send_video.py`(发送入口)
> 协议来源:逆向自 `D:\Program Files\MiniMax Code\resources\app.asar`(桌面端内置 SDK)

---

## 1. 通道结构

| 项 | 值 |
|---|---|
| 配置文件 | `~/.minimax/wechat-channel.yaml`(可用 `WX_CHANNEL_CFG` 覆盖) |
| botToken | 配置文件里的 `botToken` 字段(或环境变量 `WX_BOT_TOKEN`) |
| ilinkBotId | 配置文件里的 `ilinkBotId` 字段 |
| API 主机 | `https://ilinkai.weixin.qq.com/` |
| CDN 主机 | `https://novac2c.cdn.weixin.qq.com/c2c` |
| 目标 chatId | 配置文件里的 `ownerSenderId`(或环境变量 `WX_CHAT_ID`) |
| 通道版本 | `2.4.6` |

**关键**:上传走 `novac2c.cdn.weixin.qq.com`,API 走 `ilinkai.weixin.qq.com`。
用 API 主机做上传会 404——`/upload` 只存在于 CDN 边缘节点。

---

## 2. 发送流程

```
① getuploadurl   → 拿 upload_full_url / upload_param
② AES-128-ECB 加密 (PKCS7 padding)
③ POST CDN /upload → 响应头 x-encrypted-param
④ sendmessage    → item_list 带 media 元数据
```

### 鉴权头
```
Authorization: Bearer <botToken>
AuthorizationType: ilink_bot_token
X-WECHAT-UIN: base64(random_uint32)
iLink-App-Id: bot
iLink-App-ClientVersion: encode('2.4.6')   # 2.4.6 -> 132102
Content-Type: application/json
```

### 消息体
```json
{
  "msg": {
    "from_user_id": "",
    "to_user_id": "<chatId>",
    "client_id": "mcode-<timestamp>-<rand>",
    "message_type": 2,
    "message_state": 2,
    "item_list": [ ...一个 item... ],
    "context_token": "<任意非空字符串>"
  },
  "base_info": { "channel_version": "2.4.6", "bot_agent": "Mavis/2.4.6" }
}
```

### item 类型
| 用途 | type | 字段 |
|---|---|---|
| 文本 | 1 | `text_item: { text }` |
| 图片 | 2 | `image_item: { media:{encrypt_query_param,aes_key,encrypt_type:1}, mid_size }` |
| 语音 | 3 | `voice_item` |
| 文件 | 4 | `file_item: { media:{...}, file_name, len }` |
| 视频 | 5 | `video_item: { media:{...}, video_size }` |

`media.aes_key` 的编码形态**必须跟 SDK 一致**,见坑 6;
`video_size` / `mid_size` = **密文长度**;
`file_item.len` = **明文长度**(字符串)。

## 3. 踩坑记录(全部实测)

### 坑 1:item 必须一条一条发
把 text 和 video 放进**同一个** `item_list` → 服务端返回 `ret:-2 invalid arguments`。
正确做法:**每个 item 单独调一次 sendmessage**(SDK 源码就是这么做的)。

### 坑 2:context_token 服务端不校验值,但不能为空
代码注释原话:
> iLink REQUIRES the inbound message's `context_token` to be echoed back on every outbound.
> Without this, the adapter sends contextToken='' and iLink silently drops the reply —
> the symptom is "agent receives, user gets nothing back".

实测:传**任意非空字符串**(如 `mcode-123`)服务端照收,返回 message_id。
传空字符串 → `ret:-2 invalid arguments`。

> 这也解释了"桌面端回复了但微信没收到":桌面端会话不是微信会话,
> 走的是本地渲染,没有 iLink 出站投递。

### 坑 3:成功判据是"有 message_id",不是 ret==0
成功响应形如 `{"message_id":7522204267208779144}` —— **没有 `ret` 字段**。
写 `d.get("ret") == 0` 会误判成失败。

### 坑 4:CDN 回查 400 是正常的
`/download` 需要微信 App 专有凭据,机器人侧无法回查自己上传的文件。
**不能用回查判断发送是否成功**,只能看 sendmessage 是否返回 message_id。

### 坑 5:文件体积
iLink CDN 对大文件不友好。1.6GB 的成片要压到 ~85MB(2Mbps H.264)才能正常投递。

### 坑 6:`media.aes_key` 必须是 hex→base64 形态(44 字符)⭐

**现象**:视频消息**发送成功**(`sendmessage` 返回 message_id),微信里也**能看到时长**
(如 `4:55`),但点开提示「播放失败」。

**根因**:`aes_key` 的编码形态不对。

SDK 的出站写法(`ilink-send.js`):
```js
function aesKeyHexToBase64(hexKey) {
    return Buffer.from(hexKey).toString('base64');   // ← 注意没有编码参数
}
```
`uploaded.aeskey` 是 **32 字符的 hex 字符串**,而 `Buffer.from(str)` 不带编码参数时
默认按 **utf8** 处理 —— 所以结果是 `base64(32 个 hex 字符的 ASCII 字节)` = **44 字符**。

> 函数名写着 "HexToBase64",但实现是 utf8,不是 hex 解码。这是 SDK 的真实行为。

**野外的两种形态**(`ilink-media.js` 的 `parseAesKey` 注释写明):
```
base64(raw 16 bytes)  -> images
base64(hex string)    -> file / voice / video
```
SDK 接收端两种都认(`parseAesKey` 会按长度 16 / 32 分支),但**微信客户端按 item 类型解析**,
视频必须用 hex 形态。

**症状为什么是"能显示时长却播不了"**:
- 服务端 prepare 阶段用的是 `getuploadurl` 请求体里的 `aeskey`(hex 原值),
  所以它能解密、能解析出时长 → 客户端显示 `4:55` ✓
- 客户端解密用的是 `media.aes_key` → 形态不对 → 解不出明文 → 「播放失败」✗

**修复**(`src/ilink_client.py` 的 `aes_key_base64()`):
```python
base64.b64encode(aeskey.hex().encode("utf-8")).decode()   # 44 字符,SDK 同款
```
⚠️ 不能写成 `base64.b64encode(aeskey)` —— 那是 24 字符的 raw 形态,图片专属。

### 坑 7:`prepare failed` 与媒体、参数都无关

**现象**:`sendmessage` 返回 `{"ret":-2,"errmsg":"prepare failed"}`。
**纯文字消息也会这样**,与文件大小、编码、aes_key 形态都无关。

**判据**:同时发一条文字。
- 文字成功、视频失败 → 媒体 prepare 环节的问题
- 文字也失败 → **通道侧出站管线被卡**,与本次发送的内容无关

#### 精确边界(2026-11-01 12:5x 全量对照实验)

用 `tools/wx_channel_diag.py` 逐个端点探测,结论非常干净:

| 端点 | 结果 | 说明 |
|---|---|---|
| `getuploadurl` | ✅ 200 | 上传授权正常,`upload_full_url` 正常下发 |
| CDN `POST /upload` | ✅ | 密文上传成功,`x-encrypted-param` 正常返回 |
| `getupdates` | ✅ 200 `ret=0` | 入站长轮询正常,`sync_buf` 正常推进 |
| `getconfig` | ✅ 200 `ret=0` | **能拿到 `typing_ticket`** |
| `sendtyping` | ✅ 200 `ret=0` | **服务端接受写入**,通道在线 |
| `sendmessage` | ❌ `ret:-2 prepare failed` | **只有这一个端点被拒** |

`sendtyping` 能拿到 ticket 并成功写入,说明:**鉴权有效、bot 会话有效、chatId 有效、
出站通道在线**。被拒的只有 `sendmessage` 这一个端点。

**已排除**(全部实测,逐项对照 SDK 源码):
- 文件体积(2.7MB / 14MB / 43MB / 71MB 全试过,一样失败)
- 文件本身(完整解码 0 错误,结构与可用样本逐项一致)
- `aes_key` 形态(raw 与 hex 两种都失败)
- `context_token` 取值(空 / `sync_buf` / `get_updates_buf` / 随机 `mcode-*` 四种全失败)
- `ilink_user_id` 缺失(顶层加 / 放进 `msg` 里加,都失败)—— 注意 `getconfig` 确实要这个字段,
  但 `sendmessage` 按 SDK 的 `buildSendReq` **不带**它
- 请求结构(与 SDK 的 `buildSendReq` / `buildHeaders` / `buildIlinkBaseInfo` /
  `MessageType` / `MessageItemType` / `MessageState` / `TypingStatus` 七个枚举
  逐项比对一致,无缺失字段)
- `baseUrl` 覆盖(绑定里的 `baseUrl` 与代码默认一致)
- `chatId` 错配(与桌面端 `channel-outbound-messages.yaml` 记录的 chatId 完全一致)

**结论**:服务端对**这个 bot 的 `sendmessage` 出站管线**处于不可用状态。
不是参数问题,不是文件问题,也不是凭据/会话问题。

> ⚠️ 更正一个早期误判:曾推测是"短时限流/冷却"。实测 `sendtyping` 与 `getconfig`
> 全程正常,**限流通常不会只精确命中一个端点**,所以更像该 bot 的消息投递通道
> 被服务端单独下线(会话需重新 prepare)。

**处理**:
1. 在 MiniMax Code 里**重新扫码绑定微信通道**,重置 bot 会话(最有效)
2. 确认微信客户端没有被退出登录
3. 恢复后用 `tools/wx_channel_diag.py` 复测,`sendmessage` 通了再发视频
4. 排查期间不要反复重试 —— 连续尝试可能延长服务端侧的冷却

> ⚠️ **坑 8:`context_token` 的真实语义**(2026-11-01 核实)
> SDK 的 `sendTextMessage` / `sendVideoMessage` 里 `contextToken` 是**必填**,
> 缺失直接 `throw new Error('sendTextMessage: contextToken is required')`。
> 它的真实来源是**入站消息**:`readContextTokenFromCtx(ctx)` 从
> `ctx.contextToken` 或 `ctx.platformSpecific.contextToken` 读取,
> 桌面端还维护 `contextTokenByChat` 缓存兜底。
> 我们用伪造的 `mcode-*` 之所以也能发出去,是因为**服务端当时不校验它的值**,
> 但这是运气不是契约 —— 服务端一旦开始校验(比如 `prepare` 阶段),伪造值就会失效。
> 长期正确做法:从入站消息取真实 `context_token`,而不是伪造。

## 4. 用法

```powershell
# 发视频(参数:源文件路径 [文案])
python tools\wx_send_video.py `
  "output\wechat\2号场_龙泽_羽毛球集锦.mp4" `
  "2号场 龙泽羽毛球集锦 · 5分36秒 · 31个完整回合 · 1.1倍速 · 1080p60"
```

脚本会依次发两条消息:先文案(text),再视频(video_item)。
输出 `SUCCESS video message_id=...` 表示视频被 iLink 接受。

> **注意**:这个脚本用 `sys.path.insert` 加载 `src/ilink_client.py`,
> 请在项目根目录运行,或先把 `src` 加入 PYTHONPATH。

### 凭据从哪来
通道凭据是**本机运行时凭据,不进版本库**。`src/ilink_client.py` 按以下顺序解析:

| 项 | 环境变量 | 配置文件字段 |
|---|---|---|
| 通道配置路径 | `WX_CHANNEL_CFG` | 默认 `~/.minimax/wechat-channel.yaml` |
| botToken | `WX_BOT_TOKEN` | `botToken` |
| 会话 ID | `WX_CHAT_ID` | `ownerSenderId` / `chatId` |

环境变量优先。三者都拿不到时脚本会打印明确的修复指引并退出,不会静默失败。

### 先压到微信友好体积
项目已内置微信版压制(pipeline 的 ⑥ 阶段,`config/base.yaml` 的 `wechat` 段)。
手工压的话:
```powershell
ffmpeg -i <原成片> -c:v h264_nvenc -preset p5 -tune hq -rc vbr `
  -cq 26 -b:v 0 -maxrate 1800k -bufsize 3600k -pix_fmt yuv420p -g 120 `
  -c:a copy -movflags +faststart <输出.mp4>
```
~82MB / 1.8Mbps / 1080p60 是实测可用档位。

### 发到别的会话
`chatId` 不写死在代码里,由 `src/ilink_client.py` 的 `chat_id()` 解析:

```powershell
# 方式 1:环境变量(推荐,临时切换)
$env:WX_CHAT_ID = "<chatId>"
python tools/wx_send_video.py

# 方式 2:在通道配置文件里加 ownerSenderId / chatId 字段
```

当前用户的会话即用户与机器人的 p2p 会话。
其他会话(群聊 / 文件传输助手)的 chatId 需要另行获取。

## 5. 脚本清单

| 文件 | 用途 |
|---|---|
| `src/ilink_client.py` | 协议核心:鉴权、AES-ECB、CDN 上传、sendmessage |
| `tools/wx_send_video.py` | **发送入口**,发视频(text + video 两条) |
| `tools/wx_channel_diag.py` | **通道诊断**:逐端点探测,定位卡在哪一环(见坑 7) |
| `tools/wx_probe_img.py` | 发小图片,验证链路 |
| `tools/wx_probe2.py` | 只读探测:token 有效性 + CDN 授权 |
| `tools/wx_probe3.py` | 探测 sendmessage 参数校验规则 |
| `tools/wx_probe4.py` | 探测 context_token 是否校验值 |
| `tools/wx_getctx.py` `tools/wx_poll.py` | 尝试用 getupdates 取真实 context_token |
| `tools/wx_verify.py` `tools/wx_verify_img.py` | CDN 回查验证(见坑 4) |

> `wx_probe*.py` / `wx_verify*.py` 是排查阶段的一次性脚本,
> 日常使用只需 `tools/wx_send_video.py`。
>
> **发送失败时先跑 `tools/wx_channel_diag.py`** —— 它会告诉你问题在通道还是在媒体,
> 不用盲目重试上传大文件。

### 诊断工具用法

```powershell
# 全量探测(含一条 text 探活,会在微信里出现 "diag")
python tools\wx_channel_diag.py

# 只读探测,绝不发送任何消息
python tools\wx_channel_diag.py --no-send
```

输出三种结论:
- **通道全绿** → 通道正常,问题在媒体形态(坑 5 / 6)
- **sendmessage 被拒、其余全绿** → 服务端出站管线故障(坑 7),需重新扫码绑定
- **getuploadurl / CDN 挂** → 上传链路问题(坑 5)
