# 羽毛球长视频集锦 · 操作流程 v5(完整回合 + 统一变速)

> 场景:2 场活动录像(115 分钟 / 8GB / 1080p60 HEVC),剪成两条 ≤6 分钟集锦 + 配乐。
> 版本: v5(2026-10-31 第二轮修订)
> - v4:修复卡顿(VFR)、串行构建、击球瞬态选段、混合变速
> - **v5:回合完整性(发球→得分)+ 统一 1.1x 变速**

## 配置体系(所有参数的唯一来源)

参数全部在 `config/base.yaml`,代码里不再有魔数。改动参数不用改任何 Python 文件。

```
config/base.yaml  <  --profile <名字>(可重复)  <  --set key=value(可重复)
```

| 段 | 管什么 |
|---|---|
| `source_dir` / `clips` | 素材位置与场次清单 |
| `analysis` | 特征提取与击球检测阈值(`hit_*`、`rally_max_gap` 等) |
| `select` | 选段:边界余量、评分权重、时长分档、剔除判据 |
| `build` | 切片余量与构建阶段的最小间隔 |
| `encode` | 帧率/画幅/码率/codec 参数 |
| `mix` / `music` | 混音与配乐床 |
| `wechat` | 微信版压制(未列出的编码项继承 `encode`) |
| `output` | 母版/微信版/工作目录 |
| `ilink` | 微信通道协议参数 |

常用命令:

```bash
python src/reelconf.py                                  # 打印当前生效的完整配置
python src/reelconf.py --profile short-60s              # 看叠加 profile 后的配置
python pipeline.py --profile short-60s                  # 按 profile 跑
python pipeline.py --set encode.cq=24                   # 临时改一个值
python pipeline.py --only m3 --skip wechat              # 只跑一场、不出微信版
```

### 加一个新参数

1. 在 `config/base.yaml` 对应段里加一行(带注释说明为什么是这个值)
2. 代码里用 `cfg.at("section.key")` 读它

`src/reelconf.py` 会在开工前校验必填项与类型,缺了会立刻报出是哪个路径,
不用等跑完十几分钟才发现。

### 换一套输出规格

不必改 `base.yaml`,在 `config/profiles/` 加一个只写差异的文件即可,
例如 60 秒竖屏版:

```yaml
# config/profiles/short-60s.yaml
select: {target_seconds: 60, speed: 1.0}
encode: {scale: "1080:1920", fps: 30, gop: 60, cq: 20}
wechat: {enabled: false}
```

## v5 的两个新要求与解法

### 要求 1:回合剪辑完整,从发球到得分

v4 的边界是固定偏移(第一拍前 0.9s ~ 最后一拍后 1.6s),必然切在发球之前或得分之后。

**三次失败尝试**(都记录在案,避免重蹈):

| 尝试 | 思路 | 失败原因 |
|---|---|---|
| v3 | 运动能量找"静止→活跃"转换点 | 羽毛球是连续对打,回合间隙极短,画面运动能量几乎不降到静止 → 159 个回合被判 `start_unclear` |
| v4 | 音频找"静默期" | 这段录像**全程有场地背景噪声**(RMS 恒在 -31dB),不存在绝对静默 → `gap_after` 恒为 0 |
| v4b | 全局分位当静止阈值 | 同上,场地噪声使阈值失效 |

**v5 的正确解法**:用**局部相对能量**判据。

```
音频 RMS → 0.2s 重采样(取窗内 max,保留瞬态)
        → 减去 5s 滑动均值(消除慢漂移) = 相对能量 rel
        → 归一化
```

- **起点**:从第一拍向前回溯,直到 rel 回升到局部基线以上 → 活动重新开始 = 发球准备
- **终点**:从最后一拍向后延伸,直到 rel 跌回基线以下 → 得分后的收尾
- **得分佐证**:末拍后 0.2~2.2s 的 rel 峰值须显著高于回合内击球的 rel 中位
- **固定余量**:发球常因太轻被瞬态检测漏掉 → 起点固定回溯 0.9s,终点固定延伸 1.2s

**"不确定"的判定与移除**:

| 原因 | 判据 | 3号场 | 2号场 |
|---|---|---|---|
| `boundary_split` | 首拍前与末拍后**都**无明显能量变化 → 可能是长回合被切开的一段 | 26 | 29 |
| `no_score_evidence` | 末拍后 rel 峰值不显著(≤ 1.12× 回合基准且 < 0.25) → 缺得分响动 | 94 | 105 |
| 合计移除 | | **120** | **134** |

结果:3号场 101 个候选 → 选 41 个;2号场 118 个候选 → 选 31 个。均为 330 秒。

### 要求 2:统一 1.1x 变速

v4 是混合变速(高速原速 / 慢节奏 1.2x / 其余 1.1x)。v5 统一:

```python
def pick_speed(seg, base=1.1):
    return base    # 所有片段固定 1.1x
```

实测 1.1x 后击球间隔中位 0.69s → 0.63s,节奏依然清晰。

## v1 的三个缺陷与根因(v4 已修复,保留记录)

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **画面卡顿** | 一卡一卡 | `-r 60 -vsync cfr` 把 VFR 源强转 CFR,ffmpeg 丢弃运动帧后用**复制帧**补齐 → 产生 12485 个"画面定住"的静止帧 | `fps=60:round=near` 滤镜重采样;拼接用 **concat filter** 而非 concat demuxer |
| **3号场开头是2号场** | 开头 17.8s 内容错乱 | 两个构建任务**并发共用同一个临时目录** `_build`,2号场在失败前已覆写 `seg000/seg001`,3号场拼接时读到了它们 | 每个成片用**独立临时目录**;构建任务**串行**执行 |
| **高光质量差** | 多为 1-2 拍短促对抗 | v1 用运动能量窗口取峰 —— 运动能量高可能只是"换人/走动/穿帮" | 改为**击球瞬态检测**,以"回合"为单位选段,强制 ≥4 拍 |
| **成片 1.5GB 超大** | 5分半的片子 1.5GB | `-cq 17 -b:v 0` 配 `-rc vbr`:NVENC 下 `-b:v 0` = 无码率上限,羽毛球全画面高频运动直接把码率顶到 **39 Mbps**(源仅 12 Mbps) | 加 `-maxrate 12000k -bufsize 24000k` 兜底,`-cq 22` → **12 Mbps / 495 MB** |

## 0. 为什么"长视频剪集锦"不能只靠编辑器

8GB / 115 分钟拖进剪辑器逐帧找高光不可行(得看 6900 秒画面)。
分层策略:

| 阶段 | 工具 | 作用 |
|---|---|---|
| 找高光 | 音频瞬态检测 + 运动能量 | 115 分钟 → 800+ 回合候选 |
| 筛高光 | 自动遮挡过滤 + 逐帧视觉核验 | 剔除穿帮/捡球/近景 |
| 切片 | ffmpeg + NVENC | 精确切出,统一规格,消除 VFR 抖动 |
| 拼接 | concat filter | 时间轴天然连续 |
| 配乐 | Matrix 音乐生成 + ffmpeg 混音 | 生成 BGM 并铺满时长 |

## 3. 击球瞬态检测(核心创新)

脚本 `detect_hits.py`。这一步替代了 v1 的运动能量主算法。

**原理**:羽毛球击球 = 极短促的高频冲击音。一个"回合" = 一串间隔规律的击球瞬态。

```
astats=metadata=1:reset=10,ametadata=print:key=lavfi.astats.Overall.RMS_level
```
→ 10ms 短时 RMS 包络 → 一阶差分取上升沿 → 局部峰值 + **自适应阈值**(局部中位数 +8dB,适应场地嘈杂) → 最小间隔 0.16s 合并。

再按间隔 ≤1.6s 聚类成回合,统计拍数与间隔标准差。

**本次结果**:
| | 2号场 | 3号场 |
|---|---|---|
| 击球数 | 2505 (0.77/s) | 2217 (0.60/s) |
| 回合(≥2拍) | 416 | 427 |
| 回合(≥4拍) | 252 | 221 |
| 回合(≥8拍) | 82 | 61 |
| 回合(≥12拍) | 36 | 13 |
| 最长回合 | **44 拍 / 28.6s** | 18 拍 / 13.8s |

> 想把某个极限回合单独剪出来看:
> ```bash
> python tools/export_rally.py --clip m2 --longest
> ```
> 边界与主流程一致(命中最终选段则复用其边界,否则单独跑 `select_v5` 取边界),
> 默认 1.0x 原速 + 保留原声,便于听清每一拍。
| 击球间隔中位 | 0.690s | 0.760s |

> 为什么这个维度更强:运动能量高可能是"换人/走动",而击球瞬态是**真的在打球**,
> 且拍数直接反映回合激烈程度,间隔标准差反映连贯性。

## 4. 选段 v2

脚本 `select_v2.py`。以**回合**为单位,不用滑动窗口:

```
评分 = 0.40×拍数权重(对数饱和,12拍封顶1.6)
     + 0.25×连贯性(1/(1+间隔标准差))
     + 0.20×时长适宜度(6-16s满分,16-26s 0.75,更长 0.5)
     + 0.15×运动强度
```

**片段边界**:从第一拍前 0.9s 到最后一拍后 1.6s —— 保证起止落在回合边缘,**不切在多拍中间**。

**遮挡过滤**(自动):
- 回合内平均击球间隔 <0.30s 且拍数>12 → 衣物摩擦/走路造成的密集瞬态
- 回合内运动能量峰值 >0.88 → 近景人物贴镜头

## 6. 切片 + 拼接(v4 两阶段)

脚本 `build_v4.py`。**为什么分两阶段**:单个 filter_complex 里放 31 个 trim,
ffmpeg 仍要从头顺序解码整个 3688s 源文件,极慢(15分钟+)。

### ⚠️ 码率参数:必须同时给 `-maxrate`/`-bufsize`

**实测踩坑**:v4 初版用 `-cq 17 -b:v 0` 配 `-rc vbr`,成片 **39 Mbps**,
比源素材(12 Mbps)还高 3.3 倍,5分半的片子 **1.5 GB**。

原因:NVENC 的 VBR 模式下 `-b:v 0` 表示"无码率上限",`-cq 17` 又要求高质量。
羽毛球是全画面高频运动(球员跑动 + 球拍高速挥动 + 球网细纹),每帧都难压,码率直接顶满。

**正确参数**:
```
-c:v h264_nvenc -preset p5 -tune hq -rc vbr \
-cq 22 -b:v 0 -maxrate 12000k -bufsize 24000k \
-pix_fmt yuv420p -g 120
```

对照实验(同一段 20s 高运动素材,源 12Mbps):

| 方案 | Mbps | 6分钟估算 | 画质 |
|---|---|---|---|
| `-cq 17 -b:v 0`(初版) | 20.8 | **842 MB** | 基准 |
| `-cq 23 -b:v 0` | 9.8 | 398 MB | 100%像素对比无差异 |
| `-cq 22 -maxrate 12M` | 11.0 | 445 MB | 无差异 |
| `-cq 24 -maxrate 12M` | 8.4 | 341 MB | 无差异 |
| `-cq 26 -maxrate 10M` | 6.4 | 260 MB | 无差异 |

> 100% 像素裁切对比(球衣衣褶、球拍线、空调纹理)在 cq17/23/24/26 之间
> **肉眼完全分不出**。码率该降就降。

### 阶段 1:逐段精确切片
```
-ss <起点> -i <源> -t <时长>
-vf "fps=60:round=near:start_time=0,scale=1920:1080:flags=lanczos[,setpts=PTS/speed]"
-an -vsync cfr -r 60
-c:v h264_nvenc -preset p5 -tune hq -rc vbr -cq 22 -b:v 0 -maxrate 12000k -bufsize 24000k -g 120
```
- `-ss` 在 `-i` **前** → 输入端秒级跳转,不必从头解码
- **`fps` 滤镜**重采样(不是 `-vsync cfr`)→ 基于时间戳线性重采样,消除 VFR 抖动

### 阶段 2:concat filter 拼接
```
[0:v][1:v]...[30:v]concat=n=31:v=1:a=0[cat];[cat]fps=fps=60:round=near:start_time=0[outv]
```
concat filter 保证**所有片段共享一条连续时间轴**,无 pts 跳变。
两阶段用**相同**的码率约束参数,避免二次编码时码率再放大。

> ⚠️ 绝不要用 `concat demuxer + -c copy`:它按各文件容器时长算偏移,
> VFR 源的时长取整误差会累积成时间轴断裂。

## 7. 混合变速

`build_v4.py` 的 `pick_speed()`:

| 条件 | 速度 | 理由 |
|---|---|---|
| 回合内最小击球间隔 <0.28s | **1.0x 原速** | 高速扣杀加速会糊掉 |
| 拍数≥12 且平均间隔>0.6s | **1.2x** | 慢节奏拉锯,加速提升紧凑度 |
| 其他 | 1.1x | 轻度加速 |

实测:1.2x 后击球间隔中位 0.69s→0.575s,节奏仍清晰可辨。
最快 1% 的击球(0.18s→0.15s)会糊 —— 这就是高速回合保持原速的原因。

变速用 `setpts=PTS/speed` 插在 fps 滤镜**之后**,保证输出仍是等距 60fps。

## 8. 配乐

```bash
mcode-tools connector tools --keyword music
mcode-tools connector tool connector__matrix__batch_text_to_music
mcode-tools connector call connector__matrix__batch_text_to_music --args-file args.json
mcode-tools get_asset_url <node_id>
```

一次最多 5 段,单段只有 19-63s。所以:生成 6 段 → `acrossfade=d=1.2` 拼成 189s 基础床 →
再 `acrossfade=d=1.5` 循环到目标时长 → 整体 `afade` 淡入淡出 + `alimiter`。

混音(视频流 copy):
```
-i video -i bgm -filter_complex "[1:a]afade=...,volume=0.8,alimiter=limit=0.95[aout]"
-map 0:v -map [aout] -c:v copy -c:a aac -b:a 256k -shortest
```

## 11. 踩过的坑

| 坑 | 原因 | 解决 |
|---|---|---|
| **画面卡顿** | `-vsync cfr` 补复制帧 | `fps=60:round=near` 滤镜 + concat filter |
| **成片 1.5GB** | `-cq 17 -b:v 0` 在 NVENC VBR 下无码率上限 | 加 `-maxrate`/`-bufsize`,`-cq 22` 即够(100%像素对比无差异) |
| **3号场混入2号场** | 并发构建共用临时目录 | 独立临时目录 + 串行执行 |
| 帧差比判不出遮挡 | HEVC 压缩噪声淹没高频 | 放弃自动检测,改视觉核验 |
| 肤色 blob 全场命中 | 暖光下紫色地板落入肤色区间 | 收紧阈值+限定下半部仍不可靠,最终用视觉 |
| OpenCV 5.0 无 `CascadeClassifier` | 5.0 移除 Haar 级联 | `FaceDetectorYN`(需模型文件)或换思路 |
| `COLOR_BGR2YCrCb` 报错 | 常量改名 `COLOR_BGR2YCR_CB` | 用 `dir(cv2)` 确认后再写 |
| ffmpeg `file=` 路径冒号报错 | filter 参数分隔符冲突 | `-filter_complex` + 转义,或改走 stderr |
| 逐帧 `select='eq(n,...)'` 极慢 | 需从头解码全部帧 | `-ss` 输入端定位 |
| 单 filter 多 trim 极慢 | 仍须顺序解码整个源 | 两阶段:先切片再 concat |
| Python 逐像素分析候选太慢 | 纯 Python 循环 57k 像素×115 候选 | 改用 ffmpeg 滤镜批量计算 |
| PowerShell `cd X && for` 报错 | 语法不同 | `ForEach-Object` + 分号 |
| 含中文路径时 `Get-ChildItem` 空结果 | 控制台编码 | 改用 Python `os`/`glob` |
