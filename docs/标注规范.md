# 回合标注规范

> 用途:给"回合识别"算法做 ground truth,让 precision / recall / F1 有据可依。
> 规范写死,标注过程可复现、可复查 —— 标注质量决定评测可信度,所以边界规则必须明确。

---

## 一、什么算一个"回合"(标注对象定义)

**一个回合 = 从发球到得分,双方连续击球直到一方失分的那一段比赛。**

判定要点:

| 要素 | 规则 |
|---|---|
| 起点 | **发球动作**开始的那一瞬间(不是球出手,是发球方开始准备抛球) |
| 终点 | **得分成立**之后的一个瞬间(通常是最后一拍击球 + 0.5~1.5s 的收尾) |
| 包含 | 回合内的来回击球、随球移动、跑动、换手(击球方不变) |
| 不包含 | 捡球、换人、走位等待、暂停、聊天、场外活动 |

**必须是一个完整回合**。以下情形**不算**独立回合:

- 一个真实回合被中断(中间有人挡镜头、镜头切走)→ 仍算**一个**回合,标注时按整段记,并在 `note` 里写明中断
- 同一回合里球员击球后倒地/摔倒 → 仍算**一个**回合
- 连续得分(同一方连得 2 分,中间没有换发球流程)→ 算**两个**回合,各自从发球开始

---

## 二、边界怎么定(容差 ±0.5s)

标注时只看**画面**,不看检测器给的时刻 —— 否则就是拿检测结果验证检测结果(自证循环)。

- 起点 = 画面里**开始出现发球动作**的那一帧,往前取整到 0.5s
- 终点 = **最后一拍击球**那一帧往后 0.5~1.5s(留出得分反应),取整到 0.5s
- 允许误差 **±0.5s**。评测匹配用的是"重叠时长 / 标注时长 ≥ 0.5",±0.5s 的误差不会影响判定
- 如果边界实在看不清(比如镜头被挡),按能看清的那一侧标,`note` 写"边界不清"

> 为什么不是 ±0s:联系表抽帧是 0.5s 粒度,人眼在动态画面里也判不到 0.1s。
> 卡到 ±0.1s 只会逼出"猜数字"的标注,那是假标注。

---

## 三、拍数怎么数

- **拍数 = 回合内双方的击球总次数**(含发球那一拍)
- 按**声音 + 画面**一起数:击球声清晰可数时以声音为主,画面上 racket 触球也计入
- 只有一个回合且明确是长回合时,数不准就写 `shots_uncertain: true` 并给出估计值

## 四、标注流程(工具化,可复现)

```bash
# 1. 生成联系表(抽帧 + 候选回合行 + 空档扫描)
#    配置里声明了几个窗口,就一次跑完几个窗口,每个窗口一个子目录 w<起>-<止>/
python tools/annotate_rounds.py --video <src.mp4> --hits work/analysis/c3.hits.json \
    --out-dir work/sheets/ann --profile club-2026-11-07

# 2. 人工看图判定 → 写 eval/ground_truth/<clip>_<start>-<end>.json(一个窗口一个文件)
# 3. 跑评测
python tools/eval_rounds.py --gt eval/ground_truth --hits work/analysis/c3.hits.json \
    --segments work/analysis/c3.v5.json --out eval/reports/c3.json
```

联系表怎么读:

- `w<起>-<止>/cand_NN.png` —— **每行一个候选回合**,行首是 `#编号 起点-终点 拍数`,行内 6 帧横跨
  "候选前后各 1.5s"的上下文,每帧左下角是**绝对时间戳**
  → 逐行判定:**真回合 / 假回合**;真回合还要看首帧是不是已经在发球、末帧是不是已经结束,
  据此修正起点/终点
- `w<起>-<止>/gap_NN.png` —— **空档扫描**:候选之间没被任何候选覆盖的区间,每 2s 一帧
  → 用来抓**漏检**(检测器没认出来的回合)。看到有人在打球,就是漏检,补一条标注
- `w<起>-<止>/candidates.json` —— 候选清单,`#编号` 与联系表行首一一对应

## 五、常见的坑(标注时容易搞错的地方)

| 现象 | 正确处理 |
|---|---|
| 捡球时球拍碰到地面(有响声) | **不是击球**,不算拍数,不构成回合 |
| 球员走动脚步声、衣物摩擦 | 不算击球 |
| 球落地弹跳的声音 | 不算击球(落地是得分后的事) |
| 一方明显没在打(另一个人在场边) | 不算回合 |
| 中途换人 | 换人发生在回合之间,不构成回合边界 |
| 连拍(两拍间隔 < 0.2s) | 算 2 拍 |
| 回合很长(≥30 拍) | 照常标,这是 R4 的评测对象,不能漏 |

> 这些坑和 `docs/踩坑记录.md` 里的"衣物摩擦/走路造成密集瞬态"是同一类问题 ——
> 检测器会把这些误当击球,标注时不要跟着检测器的错误走。

## 六、标注文件格式

`eval/ground_truth/<clip>_<start>-<end>.json`:

```json
{
  "source": "20261107_龙泽_3号场.mp4",
  "clip": "c3",
  "window": {"start": 1200.0, "end": 2400.0},
  "annotator": "agent:视频剪辑执行员",
  "method": "contact-sheet visual review (tools/annotate_rounds.py)",
  "tolerance_seconds": 0.5,
  "rallies": [
    {"id": "r000", "start": 1203.5, "end": 1210.5, "shots": 8, "note": ""}
  ]
}
```

字段说明:

| 字段 | 说明 |
|---|---|
| `id` | 回合编号,同一文件内唯一 |
| `start` / `end` | 源视频绝对时间(秒),按第二节的规则取 |
| `shots` | 拍数(按第三节) |
| `note` | 备注(边界不清 / 中断 / 特殊情形),可为空 |
| `shots_uncertain` | 拍数数不准时置 true |

## 七、评测怎么读(哪些指标说明什么)

| 指标 | 含义 | 掉了说明什么 |
|---|---|---|
| `detection.precision` | 认出来的回合里有多少是真的 | 误检变多(捡球/走动被当成击球) |
| `detection.recall` | 真回合里认出了多少 | 漏检变多(长回合被切开、击球被漏) |
| `detection.f1` | 两者综合 | 总体识别质量 |
| `shot_count_mae` | 拍数平均绝对误差 | 拍数被低估(长回合会因此达不到 ≥30 拍的门槛) |
| `segment.complete_rally_rate` | 选出的片段里有多少是"从发球到得分"的完整回合 | 片段被切在中间了 |
| `long_rally.recall_reel` | ≥30 拍的长回合有多少进了成片 | R4 没达标 |

## 八、扩标注时怎么做

窗口分成两类,各管一件事,**都不能事后按结果挑**:

### 8.1 普通窗口(管 R2:回合识别 P/R/F1)

> 从第 20 分钟(1200s)起取连续 20 分钟;
> 若该窗口内标注回合数 < 20,则按同样步长向后顺延到第一个满足条件的窗口。

密度高低的窗口都会出现(打球密集 / 中场休息 / 换边),全都按规则处理。

### 8.2 长回合专窗(管 R4:长回合召回)

长回合是稀缺样本:一个 80 分钟的场次里可能一个都没有(本批 11月7日 3号场实测:
≥30 拍 **0 个**,≥20 拍 4 个)。普通窗口只盖住其中一部分,长回合指标就会退化成
"0 个样本 → 0/0",那不叫验收。

**规则(事先声明,不看结果再改):**

1. 用检测层跑出该批所有 **≥ N 拍**的回合,N = 该批 profile 的 `select.long_rally_shots`
   (base 是 30;11月7日 这批是 20 —— 见 `config/profiles/club-2026-11-07.yaml`);
2. 取这些回合里**最早的起点**与**最晚的终点**,得到"最小覆盖跨度"
   (本批 = 560.5s ~ 3037.6s);
3. 跨度两端各留 `annotation.context_seconds`(默认 1.5s)上下文 ——
   不留就看不清第一拍是不是发球、最后一拍之后是不是已经结束,边界无从判;
   (本批 = 559.0s ~ 3039.1s)
4. 把跨度与普通窗口合并,**去重后**切成若干**连续、不重叠**的标注文件,一个文件一个 `window`;
5. 拆分点固定取整分钟,不许按"哪个窗口拍得好看"调整。

> 为什么规则要事先写死:如果按"打完的结果"反推窗口,
> 就是拿检测结果挑窗口,评测会自证循环。规则只依赖"长回合有多长、在哪",
> 不依赖"检测器准不准" —— 边界和拍数仍然必须人眼看画面判定(见第二节)。

### 8.3 扩窗之后

1. 新的窗口存成新的 json 文件,`window` 字段写清起止
2. `tools/eval_rounds.py` 会自动把目录下所有标注文件合并评测
3. 改了算法后跑:

```bash
python tools/eval_rounds.py --gt eval/ground_truth --hits ... --segments ... \
    --compare eval/baseline/baseline.json
```

任何指标下降超过 `eval.regression_tolerance` 都会以退出码 1 结束 —— 可以直接挂 CI。

### 8.4 阈值口径必须两边一致

`eval.long_rally_shots`(评测层判定"什么算长回合")必须与
`select.long_rally_shots`(选段层强制纳入的门槛)取同一个值。
本批两者都是 20;base 两者都是 30。
评测报告里 `long_rally.threshold_shots` 会打印实际生效的口径 ——
**汇报时必须带上这个数**,不能默认说"≥30 拍",否则验收方会按错的口径理解指标。

## 九、判定「是不是一回合」必须按候选瞬态时刻抽帧(2026-11-07 裁定)

**规则**:判定一段是不是回合、该段有几拍,**必须**在**候选击球时刻**上抽帧,
**不能**按固定间隔抽帧。

原因:羽毛球回合本身是**间歇**的 —— 两拍之间球员在等球。固定间隔采样(例如
每段 16 帧、间隔 6.4s)几乎必然落在等待间隙上,于是:

- 真回合被误判成「不是回合」(验收员对段#3、段#5 的「真实对打」判定据此作废);
- 「站着不动」被误判成「在打」。

**做法**(	ools/gt_review_sheet.py):

1. 候选击球时刻由**独立音频包络法**给出(6ms 窗 / 2ms 步 -> 局部极大值 ->
   相对本段中位数 >= +11dB;0.30s 内相邻瞬态按「拍+球」双响规则合并为一次候选)。
   该链与 src/detect_hits.py 的 rise / offset / thresh 无任何共享参数 ——
   **GT 不允许由检测器输出反推**。
2. 每个候选时刻抽 1 帧**主球场 ROI**(4fps 网格,±0.125s),拼成复核表。
3. 人眼逐格判定:前景主球场这一拍有没有**击球动作**(挥拍出手 / 弓步 / 扑救 /
   球在空中)。有 -> 记 1 拍;站立持拍、走动、弯腰捡球 -> 记 0 拍。
4. shots = 判定为真的候选数;同时记 shots_uncertainty 带。

**判据口径**:is_rally=false 的区间写进 val/ground_truth/c3_negative_rallies.json
(负样本单独成集,不计入长回合召回);is_rally=true 的写进
val/ground_truth/c3_long_rallies.json。每一拍都要能在复核表上指出来。

**证据**:work/sheets/gtreview/<id>.png
